# 公開版の機能とデータの取り扱い（2026-10-21 時点）

初回リリースから**課金あり**（月額300円、最初の1か月無料）。App プライバシー申告と
プライバシーポリシーの確認用に、いま実装がどうなっているかをまとめたもの。

## 1. 機能とその見え方

タブは状況によって出たり消えたりする。判定は2つだけ。

| タブ | 中身 | 出ない条件 |
|---|---|---|
| home | 今日のやること・家事・天気 | — |
| calendar | Google カレンダー + 手入力の予定 | — |
| cook | 献立カレンダー | **課金ゲート** |
| shopping | 買い物リスト（共有 / 非公開） | — |
| split | 割り勘・固定費 | **1人世帯のとき（ソロ）** |
| recipe | レシピ | **課金ゲート** |
| 設定 | 世帯・家事・カレンダー・通知・アカウント削除 | — |

- **課金ゲート**: `household_entitled()` が true のときだけ。世帯の**全員**が権利
  （購入 or 運営の付与）を持っている必要がある。1人でも欠けると献立とレシピのタブが出ない。
- **ソロ判定**: フラグではなく人数から導出（`memberCount <= 1`）。割り勘は2人前提のため。
- 購入導線（設定の premium 欄・ペイウォール）は `NEXT_PUBLIC_BILLING_ENABLED` が
  `true` のときだけ描画される。未設定の間は一切出ない。

## 2. データはどこにあるか

**保存先は Supabase（公開版専用プロジェクト）のみ。** 16テーブル、全てに RLS 有効。

| 種類 | 表 | 見える範囲 |
|---|---|---|
| 世帯・メンバー | households, household_members | 自分が属する世帯 |
| やること | shared_todos | 世帯 |
| 家事ルーティン | routine_definitions, routine_completions | 世帯（user_id は担当者） |
| 買い物 | shopping_items | 世帯。ただし `user_id` 入りは**本人のみ** |
| レシピ | recipes | **持ち主本人 + 同じ世帯にいる間だけ相手にも** |
| 献立 | meal_plans | 世帯（部屋をまたぐ） |
| 予定 | local_calendar_events, calendar_settings | 世帯（user_id は作成者） |
| 割り勘 | split_sessions, split_subscriptions, family_card_totals | 世帯 + **現在の部屋のみ** |
| 割り勘の設定 | split_settings（締め日・負担比率） | 世帯 |
| 固定費の項目 | split_utilities（通信・電気など） | 世帯（部屋をまたぐ） |
| 固定費の金額 | split_utility_amounts | 世帯 + **現在の部屋のみ**。書き込みは関数（`set_split_utility_amount`）経由 |
| Google トークン | user_tokens | **クライアントからは本人も不可**。サーバーだけが読み書きする（AES-256-GCM で暗号化） |
| 表示名・カレンダー色 | member_profiles | 世帯 |
| 課金状態 | subscriptions | 本人（RevenueCat の webhook が書く） |
| 運営による付与 | premium_grants | だれも読めない（`premium_status()` 経由で本人に伝わる。相手には有無だけ） |

画像（レシピ写真）は Supabase Storage の `recipes` バケット。**公開URLで配信される**ため、
URL を知っていれば誰でも見られる。推測は困難だが、秘密ではない。

### 日記は載せない

`DiaryTab` はどこからも呼ばれておらず利用者は到達できなかったため、
2026-09-12 にコード（`src/components/diary/`, `src/store/diaryStore.ts`, `DiaryEntry` 型）と
`diary_entries` 表をまとめて削除した。公開版に日記機能は無い。

### 「部屋」による区切り

`households.pairing_started_at` が現在のペアの開始時刻。割り勘3表と共有買い物アイテムは、
この時刻以降の行しか見えない（restrictive ポリシー）。
**目的**: 1人に戻ってから別の人を招待したとき、前の相手とのお金の記録が新しい相手に
見えてしまうのを防ぐ。レシピ・献立・やること・家事は区切っていない（前セッションの
判断待ち。docs/handoff.md の「未決の設計判断 A」）。

## 3. 外部に出るデータ

ここが App プライバシー申告で申告が要る部分。

| 送り先 | 何を送るか | いつ |
|---|---|---|
| **Supabase** | 上記すべて、メールアドレス、認証情報 | 常時 |
| **Google** | OAuth ログイン、カレンダーの読み取り | ログイン時・カレンダー表示時 |
| **Anthropic (Claude API)** | **レシピURLのページ内容、またはレシピの写真** | レシピの取り込み実行時 |
| **OpenWeatherMap** | **緯度経度** | home タブを開くたび |
| RevenueCat | 購入情報 | 初回リリースでは**送らない**（無効化済み） |

**通知は外に出ない**。「今日の家事」の通知は端末が自分で予約して自分で鳴らす
ローカル通知で、サーバーも APNs も経由しない。デバイストークンも保存しない。
通知の設定（オン・オフと時刻）は端末の localStorage にだけ置き、世帯では共有しない。
App プライバシー申告で通知に関して申告するものは無い。

**見落としやすい点**:

- レシートの撮影読み取りは 2026-09-12 に削除した（割り勘は手入力のみ）。
  画像を外部に送る経路はもう無い。
- 天気は緯度経度を OpenWeatherMap に送る。座標が無い場合は
  `x-vercel-ip-latitude`（接続元IPから推定した位置）にフォールバックする。
  **Vercel 固有のヘッダーなので、別のホストに移すとこの部分は動かなくなる。**
- Google のリフレッシュトークンは `localStorage` にも置いている（`authStore`）。

## 4. 消すとき

| 操作 | 何が起きるか |
|---|---|
| アカウント削除 | `auth.users` から削除。外部キーが CASCADE / SET NULL に張り直してあるので連鎖する |
| 世帯の解散 | 抜ける人は新しい1人用世帯へ。レシピ・家事・やること・献立の**複製**を持っていく |
| 解散時のトークン | `user_tokens.household_id` を付け替える。**消すだけでは相手のカレンダーが見え続ける** |
| 解散時の非公開買い物 | **行ごと削除**する。`user_id` を null にすると「みんなのもの」になり中身が見える |

**Apple のサブスクはアプリから解約できない**（App Store Server API に該当エンドポイントが無い）。
課金を入れたら、削除画面で解約画面へ誘導してチェックを入れさせる方式になる。

### Guideline 4.8: Sign in with Apple（コードは対応済み・設定が残っている）

`AuthGate.tsx` に Sign in with Apple を追加した（2026-09-12）。残っているのは設定作業:

1. **Apple Developer**
   - Identifiers で **Services ID** を作る（例 `com.keikato.homeapp.signin`）
   - Return URL に `https://<ref>.supabase.co/auth/v1/callback`
   - Keys で **Sign in with Apple 用の鍵（.p8）** を作り、Key ID と Team ID を控える
2. **Supabase** → Authentication → Providers → Apple を有効化し、
   Services ID・Team ID・Key ID・.p8 の中身を入れる
3. **Supabase** → Authentication → Manual linking を有効にする
   → Apple で入った人が後から Google カレンダーを繋ぐときに使う。
   　無効でも動くが、その場合は Google での再ログインに落ちる

**Apple で入った人は Google のトークンを持たない。** カレンダーは手入力の予定だけになり、
calendar タブに「connect google calendar」が出る。そこから `connectGoogleCalendar()` が
linkIdentity で今のアカウントに Google を紐付ける（signInWithOAuth をそのまま呼ぶと
別アカウントに化けるため、識別子の有無で分岐している）。

以下は、なぜ必要だったかの記録:

`AuthGate.tsx` は `signInWithOAuth({ provider: "google" })` のみだった。

Apple のガイドライン 4.8 は、サードパーティのログインを主たるアカウント作成手段に
使う場合、**次の3条件を満たす別のログイン手段も用意すること**を求めている。

1. 集める情報が名前とメールアドレスに限られる
2. メールアドレスを隠せる
3. 同意なしに広告目的で追跡しない

**Google ログインはこれを満たさない。** 実質的に **Sign in with Apple の追加が必要**。
Supabase Auth は Apple プロバイダに対応しているので、実装量自体は大きくないが、
Apple Developer 側で Service ID と鍵の作成が要る。

**これは公開前に必ず対応が要る。** 現状のままだと 4.8 で差し戻される。

### ⚠️ Google OAuth が未審査

`AuthGate.tsx` は `calendar.readonly` スコープを要求している。これは Google の
**sensitive scope**（他人に見せたくない情報）にあたるため、審査を通していないと
ログインのたびに「このアプリは Google で確認されていません」という警告が出る。

自分で試すぶんには「詳細」→「（安全ではないページ）に移動」で通過できるが、
**公開すると利用者全員がこの赤い警告を見る。** 実質そこで離脱する。

さらに、公開ステータスが「テスト中」のままだと:

- テストユーザーとして登録した人しかログインできない（上限100人）
- **リフレッシュトークンの寿命が制限される** → 利用者が定期的に再ログインを迫られ、
  Google カレンダーの表示が繰り返し壊れる

審査（verification）に必要なもの:

- OAuth 同意画面の記入（アプリ名・サポートメール・ロゴ）
- **ドメインの所有確認**（Search Console の**ドメインプロパティ**で `imbrex.app` を DNS の
  TXT レコードで検証する。`*.vercel.app` は Public Suffix List に載っていて
  「自分が所有するドメイン」として認められないので、独自ドメインが要る）
- **プライバシーポリシーの URL**（`/privacy` を使う。いまドラフトなので要確認）
- アプリのホームページ URL
- **デモ動画** — ログインの流れと、カレンダー権限を何に使っているかを映したもの
- 申請して審査を待つ（数日〜数週間）

restricted scope（Gmail や Drive 全体）ではないので、第三者によるセキュリティ監査
までは要らない。とはいえ**日数がかかるので、App Store の審査と並行して早めに出す**こと。

なお `calendar.readonly` を捨ててローカル予定だけにすれば審査は不要になるが、
Google カレンダー連携はこのアプリの主要機能なので現実的ではない。


## 3. 個人データへのアクセス（2026-10-21 監査）

全テーブルのポリシー、ストレージ、全 API を見直した。見つかって塞いだもの:

| 穴 | 何ができたか | 対処 |
|---|---|---|
| `households` の「ログインしていれば全件読める」ポリシー | 全世帯の id と招待コードの一覧を取れた | 削除。自分の世帯しか読めない |
| `household_members` の「自分の行なら insert できる」ポリシー | **招待されていない世帯に入り込み、その世帯のデータと相手の Google カレンダーを見られた**。定員・課金の確認もすり抜けた | 削除。作成と参加はサーバーだけ（`/api/household/create`, `join`） |
| `user_tokens` をクライアントから書けた | 他人の世帯を指す鍵の行を作れた | ポリシー削除（サーバーだけ）。`/api/partner-calendar` は相手を `household_members` から引く |
| レシピの `owner_id` を相手が書き換えられた | 相手のレシピを自分のものにできた | トリガーで変更禁止 |
| レシピ写真のストレージにポリシーがリポジトリに無かった（手作業） | 設定次第で他人の写真の削除・一覧の列挙ができた | recipes バケットのポリシーを作り直し、自分のフォルダ（`{user_id}/`）だけに。画像のみ・10MB まで |
| アカウント削除で写真が消えなかった | 退会後も写真が公開 URL で見られた | 削除時にストレージからも消す |
| `/api/recipe/og` がログイン不要で任意の URL を取りに行った | サーバーを踏み台に内部アドレスを叩けた（SSRF） | ログイン必須。`safeFetch` で内部アドレス・リダイレクト・大きさを制限 |
| `/api/parse-recipe` の URL 取り込み | 同上 | `safeFetch` |
| `/api/refresh-token` がログイン不要 | 他人のリフレッシュトークンを持つ人が、このアプリのクライアントシークレットで更新できた | ログイン必須 |
| `/api/weather` がログイン不要 | 天気 API の利用枠を使われる | ログイン必須 |

修正前の状態を手元の Postgres で再現し、攻撃が通ること（全世帯の招待コードの取得、他人の世帯への参加と
データの閲覧、他人の写真の削除）と、修正後はすべて拒否されることを確かめた。

**ルール（今後これを崩さないこと）**
- 世帯の所属を変える操作（作成・参加・解散・退出）はサーバーだけ。`household_members` と
  `households` にクライアント向けの insert / update / delete ポリシーを置かない
- だれでも全件読める select ポリシー（`using (true)` や `auth.uid() is not null`）を置かない
- `user_tokens` にクライアント向けのポリシーを置かない
- 利用者の入れた URL をサーバーから取りに行くときは `src/lib/server/safeFetch.ts` を通す
- 外部の有料 API を呼ぶルートはログイン必須（`requireUser` / `requireEntitled`）
- ストレージは `{user_id}/` の下だけ。ポリシーはリポジトリのマイグレーションで管理する

**まだ残っているもの**
- レシピ写真は公開 URL で配信している。URL を知っていればだれでも見られる（一覧は取れない）。
  非公開にするには、バケットを private にして署名付き URL に切り替える必要がある
- アカウント削除の「レシピを引き継ぐ」は実際には効いていない。`recipes.owner_id` が
  `on delete cascade` なので、退会した人のレシピは選択にかかわらず消える
